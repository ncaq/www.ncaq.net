# まとめ

- セルフホストしている[Forgejo](https://forgejo.org/)への転送量の99%以上を、Metaのクローラの`meta-externalagent`が占めていました
- 読まれていたのは、Forgejoの既定の`robots.txt`が`User-agent: *`宛てに断っているページばかりでした
- 同じ規則を`meta-externalagent`と`meta-webindexer`を名指ししたグループでもう一度書いたら止まりました
- 名指しを外して`User-agent: *`だけに戻したら再開し、名指しを戻したらまた止まりました
- つまりMetaのクローラは`User-agent: *`のグループには従わず、名指しされた時だけ従うように見えます
- Metaのクローラにパスの指示を伝えたい場合は、`User-agent: *`のグループとは別に名指しのグループを書く必要があります

# 前提

誤解されたくないので先に私の立場を書いておきます。

- 知識は自由であるべきなので、AIクローリング自体は常識的な範囲だとむしろ歓迎したい
  - このサイトの[robots.txt](https://github.com/ncaq/www.ncaq.net/blob/master/site/robots.txt)には、
    [Associating AI Usage Preferences with Content in HTTP](https://datatracker.ietf.org/doc/draft-ietf-aipref-attach/)の`Content-Usage: search=y, ai-use=y, train-ai=y`を書いて明示的に許可までしています。
    [feat: AI学習などへの自由な利用を機械可読に表明 by ncaq · Pull Request #472 · ncaq/www.ncaq.net](https://github.com/ncaq/www.ncaq.net/pull/472)
- Metaのことは別にそんなに嫌いではない
- むしろクローラと協力して、見ても意味がほぼないページを除外してノイズを減らしたい
- クロールを禁止するのではなく見ても無駄という程度のヒントを与えたいと思っているぐらい

なのでこの記事は「Metaのクローラをブロックしよう」という話ではありません。
「Metaのクローラに話を聞いてもらうには名前を呼ぶ必要があった」という観察の記録です。

## 用語

この記事では`robots.txt`の、

```text
User-agent: *
Disallow: /foo/
```

のような`User-agent`の行と規則のまとまりを「グループ」と呼びます。
[RFC 9309: Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html)の
[2.2. Formal Syntax](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.2)
の用語です。

`User-agent: meta-externalagent`のように特定のクローラの名前を書いたグループのことは「名指しのグループ」と呼びます。

## 来ていたクローラ

User-Agentは以下の2種類でした。

- `meta-externalagent/1.1`
- `meta-webindexer/1.1`

実際のUser-AgentはChromeやEdgeやFirefox風の文字列の末尾に、
以下のような文字列が付いた形をしています。

```text
(compatible; meta-externalagent/1.1 (+https://developers.facebook.com/docs/sharing/webmasters/crawler))
```

件数のほぼ全ては`meta-externalagent`で、
30日間で3,331,990件です。
`meta-webindexer`は3,710件でした。

Metaの公式ドキュメントの
[Meta Web Crawlers](https://developers.facebook.com/docs/sharing/webmasters/web-crawlers)
は`meta-externalagent`の用途をこう説明しています。

> The Meta-ExternalAgent crawler crawls the web for use cases such as training foundation AI models or improving products by indexing content directly.

基盤モデルの学習などのためのクローラです。

[`meta-webindexer`](https://developers.facebook.com/docs/sharing/webmasters/web-crawlers#meta-webindexer)の方はMeta AIの検索結果の品質のためのものだそうです。

> The Meta-WebIndexer crawler navigates the web to improve Meta AI search result quality for users.

# 原因

GitのセルフホストサーバのForgejoが一つのリソースに対して複数のビューを提供したり、
データをバンドルしたサイズの大きいデータを返すことで大量のダウンロードの余地を作ってしまいました。

ForgejoはそのようなURLは既定の`robots.txt`でクロールを禁止しているのですが、
Metaのクローラは従いませんでした。

## 履歴のビューの総当たり

Metaのクローラが読んでいたのは主に以下の4種類のURLです。

- `/{owner}/{repo}/src/commit/{hash}/...`
- `/{owner}/{repo}/raw/commit/{hash}/...`
- `/{owner}/{repo}/commits/commit/{hash}/...`
- `/{owner}/{repo}/blame/commit/{hash}/...`

それぞれ、
あるコミットの時点でのファイルの表示、
生のファイル、
そのファイルのコミット履歴、
[git blame](https://git-scm.com/docs/git-blame)の表示です。

30日間の件数は以下の通りです。

| 種類             | 件数    |
| ---------------- | ------- |
| `src/commit`     | 948,360 |
| `blame/commit`   | 842,740 |
| `commits/commit` | 578,520 |
| `raw/commit`     | 413,040 |

ブランチ指定の`src/branch/master/...`のようなURLはほとんど読まれておらず、
読まれているのはコミットのハッシュで固定したURLばかりでした。

つまり全てのコミットと全てのファイルと4種類のビューの組み合わせを、
総当たりで読んでいます。
このサイトのリポジトリだけでもコミットが2500以上あって記事のファイルも600以上あるので、
組み合わせはいくらでもあります。

しかし同じファイルの過去の版を何千通りも読んでも、
新しい知識はほとんど増えません。
大半のコミットでは大半のファイルは変わっていないからです。

応答はほぼ全てがステータス200で、
Cloudflareのキャッシュ状態もほぼ全てが[`dynamic`](https://developers.cloudflare.com/cache/concepts/cache-responses/#dynamic)でした。
リダイレクトで空回りしていたわけでも、
Cloudflareのキャッシュが返していたわけでもなく、
オリジンのForgejoが毎回ちゃんとHTMLを生成して返していたことになります。

## git bundleのダウンロード

転送量が特に大きかったのは`/archive/`です。

Forgejoはリポジトリを`.zip`や`.tar.gz`でダウンロードできるだけではなく、
[git bundle](https://git-scm.com/docs/git-bundle)の形式でもダウンロードできます。
Metaのクローラは以下のようなURLを読んでいました。

```text
/ncaq/www.ncaq.net/archive/739890403404ebb16ed0146f2cfaa4db74e348d0.bundle
```

このサイトのリポジトリは画像も入っているので、
bundleは1件でおよそ227MBあります。
それをコミットごとに別のURLとして落としています。
中身はほとんど同じです。

30日間で`/archive/`は8,230件、
104GBでした。
11-05は53GB、
11-06は56GBを1日で持っていっています。

Gitのリポジトリの中身が欲しいなら[`git clone`](https://git-scm.com/docs/git-clone)を1回すれば全ての履歴が手に入るのですが、
そういう賢いことはしてくれません。

## ログイン画面

ツイートに書いたログイン画面の`/user/login`は、
30日間で50万件以上読まれていました。
11-05と11-07と11-08は1日に11万件を超えていて、
その日のMetaのリクエストの大半を占めています。

Forgejoは全てのページのログインのリンクに`?redirect_to=`で今のパスを付けるので、
ページごとに別のURLとして辿っているのだと推測しています。
Freeプランではクエリ文字列を集計できないので、
確かめられてはいません。

## Forgejoの既定のrobots.txtは全部断っている

ここまでに挙げたURLは全て、
Forgejoの既定の`robots.txt`が断っています。

Forgejo 15.0.11の既定の`robots.txt`は、
`routers/web/misc/misc.go`の
[`defaultRobotsTxt`](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.11/routers/web/misc/misc.go#L61-L131)
に書かれています。
ドキュメントは[Search Engines Indexation](https://forgejo.org/docs/latest/admin/search-engines-indexation/)です。
以下は抜粋です。

```text
# The default Forgejo robots.txt
# For more information: https://forgejo.org/docs/latest/admin/search-engines-indexation/

User-agent: *
Disallow: /api/
Disallow: /avatars/
Disallow: /user/
Disallow: /swagger.*.json
Disallow: /explore/*?*

Disallow: /repo/create
Disallow: /repo/migrate
Disallow: /org/create
Disallow: /*/*/fork

(中略)

Disallow: /*/*/src/
Disallow: /*/*/blame/
Disallow: /*/*/commit/
Disallow: /*/*/commits/
Disallow: /*/*/raw/

(中略)

Disallow: /*/*/archive/
Disallow: /*.bundle$

(中略)

Disallow: /*redirect_to=*
```

`User-agent: *`のグループが1つだけあって、
`Disallow`が56個並んでいます。

- 履歴のビューは`/*/*/src/`と`/*/*/blame/`と`/*/*/commits/`と`/*/*/raw/`で断っている
- git bundleは`/*/*/archive/`と`/*.bundle$`で断っている
- ログイン画面は`/user/`と`/*redirect_to=*`で断っている

Forgejoは見ても無駄なページをちゃんと分かっていて、
全てのクローラに「ここは読まなくて良いですよ」と伝えているわけです。
実際にGooglebotとOAI-SearchBotはそれを読んで履歴のビューには来ていません。

Metaのクローラだけが従っていませんでした。

# 調査

調査した結果、
Metaのクローラは`robots.txt`の`User-agent: *`に従わず、
名指しされた時だけ従うことがわかりました。

## Metaのクローラはrobots.txtを取得していない

まず`/robots.txt`を誰が取得しているのかを調べました。

10-21から11-23までの間、
`meta-`のUser-Agentによる`/robots.txt`の取得は、
自分で送った確認を除くと0件でした。
300万件以上のリクエストを投げておいて`robots.txt`は一度も読みに来ていません。

一方で`facebookexternalhit/1.1`は毎日10件前後`/robots.txt`を取得していました。
`facebookexternalhit`はFacebookなどにリンクが貼られた時にプレビューを作るためのクローラです。
私のForgejoのトップページを4分半に1回読みに来ていて、
これはこれで何をしているのかよく分かりません。

## Metaの公式ドキュメント

[Meta Web Crawlers](https://developers.facebook.com/docs/sharing/webmasters/web-crawlers)
を読みました。
2026-11-23に読んだ時点では"Updated: May 21, 2026"と表示されていました。

`robots.txt`についてはこう書いてあります。

> By configuring the robots.txt file on your website, you can specify to the Meta web crawlers how you would prefer them to interact with your site. In order to block these crawlers, add a disallow for the relevant crawler to robots.txt.

載っている例は以下のものです。

```text
User-agent: meta-externalagent
Allow: /                    # Allow everything
Disallow: /private/         # Disallow a specific directory

User-agent: meta-externalads
Allow: /                    # Allow everything
Disallow: /private/         # Disallow a specific directory
```

- `User-agent: *`については何も書いていない。従うとも無視するとも書いていない
- "add a disallow for the relevant crawler"と、名指しを案内している
- 例は名指しのグループだけ
- パスの途中のワイルドカードについては何も書いていない

`*`を無視すると公言はしていないものの、
名指しを前提にした書き方です。

反映の時間についてはこう書いてあります。

> Please allow up to 24 hours for changes to robots.txt to take effect because crawlers may cache the contents of robots.txt for up to 24 hours.

24時間という数字自体はRFC 9309の[2.4. Caching](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.4)の範囲内です。

## 空行の仮説

最初に疑ったのは空行です。

Forgejoの既定の`robots.txt`は、
`User-agent: *`のグループの途中に見やすさのための空行があります。

RFC 9309の[文法](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.2)では空行はグループの途中にあっても構いません。
しかし1994年の元々の仕様の
[A Standard for Robot Exclusion](https://www.robotstxt.org/orig.html)
ではこうなっています。

> The file consists of one or more records separated by one or more blank lines

空行がレコードの区切りです。
この解釈で読むと、
既定の`robots.txt`の`*`に効くのは最初の空行までの5行だけで、
`/*/*/src/`などはどのグループにも属さないことになります。

Metaが古い解釈で読んでいるのではないかと考えました。

結論から言うとこの仮説は外れでした。

## 名指しのグループを足す

とは言え最初は切り分けよりクロールを落ち着かせることを優先したので、
空行を除くことと名指しのグループを足すことを同時にやりました。

[feat(seminar): Forgejoのrobots.txtでMetaのクローラを名指しして既定の規則を言い直します by ncaq · Pull Request #1736 · ncaq/dotfiles](https://github.com/ncaq/dotfiles/pull/1736)

Forgejoは`custom/public/robots.txt`があると、
既定のものの代わりにそれを返します。
[`RobotsTxt`](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.11/routers/web/misc/misc.go#L133)の実装がそうなっています。
そこに以下の形のファイルを置きました。

```text
User-agent: *
Disallow: /api/
(既定のリストを空行なしで)
Disallow: /*repo-search-archived=*

User-agent: meta-externalagent
User-agent: meta-webindexer
Disallow: /api/
(同じリスト)
Disallow: /*repo-search-archived=*
```

新しく断った場所はありません。
既定で全てのクローラに頼んでいることを、
Metaに通じるかもしれない書き方でもう一度言っただけです。

2026-11-17 15:37に配信が切り替わりました。

その後も9時間ほどは毎時1,800件のままでしたが、
11-18の01時台から1,123件、
994件、
696件、
478件、
156件と減っていって、
06時台に0件になりました。

止まりました。

## 名指しのグループを外す

止まったのは良いのですが、
空行と名指しのどちらが効いたのかが分かりません。

Forgejoに報告したところ、
[空行を除くだけで効くのかを確かめてほしい](https://codeberg.org/forgejo/forgejo/issues/15333#issuecomment-28076979)と頼まれました。
空行だけで効くのであれば、
Forgejoの既定の`robots.txt`から空行を除くだけで他のインスタンスも助かるので、
確かに切り分ける価値があります。

[feat(seminar): Forgejoのrobots.txtからMetaを名指ししたグループを外します by ncaq · Pull Request #1782 · ncaq/dotfiles](https://github.com/ncaq/dotfiles/pull/1782)

名指しのグループを外して、
空行なしの`User-agent: *`のグループだけにしました。
2026-11-20 00:32頃に配信が切り替わりました。

5時間半後の06時台に、
1,618件でいきなり再開しました。
その後は止まる前と同じ毎時1,800件前後です。
再開した最初の1時間でさっそく227MBのgit bundleを何個も落としていきました。

効いていたのは名指しで、
空行は関係ありませんでした。

Forgejoのissueでは[mahlzahn](https://codeberg.org/mahlzahn)さんも自分のインスタンスで同じ実験をしていて、
[空行を除いてもクローラは居座ったままだった](https://codeberg.org/forgejo/forgejo/issues/15333#issuecomment-28076979)と書いています。

## 既定のものに名指しのグループだけを足す

最後に、
既定の`robots.txt`には一切手を入れず、
後ろに名指しのグループを足すだけで止まるのかを確かめました。
止まるのであればForgejoの既定の`robots.txt`へ足す最小の変更が分かります。

[feat(seminar): Forgejoの既定のrobots.txtへMetaを名指ししたグループだけを足します by ncaq · Pull Request #1791 · ncaq/dotfiles](https://github.com/ncaq/dotfiles/pull/1791)

前半の1489バイトはForgejo 15.0.11の`defaultRobotsTxt`と完全に一致させました。
冒頭のコメントも、
グループの途中の空行もそのままです。

2026-11-20 21:28頃に配信が切り替わりました。

8時間半後の11-21 06:05頃に止まりました。
今回は段階的にではなく、
5分の間に0件へ落ちました。

## 結果の整理

![robots.txtの変更とMetaのクローラのリクエスト数(1時間ごと)](/asset/2026-11-23-meta-crawl-robots-txt.svg)

試した形と結果を並べると以下の通りです。

| `robots.txt`の形                                      | 配信の開始    | Metaのクロール     |
| ----------------------------------------------------- | ------------- | ------------------ |
| 既定のもの(空行あり、`*`だけ)                         | 11-17より前   | 続く               |
| 空行なしの`*`のグループと、その後ろに名指しのグループ | 11-17 15:37   | 14.5時間後に止まる |
| 空行なしの`*`のグループだけ                           | 11-20 00:32頃 | 5.5時間後に再開    |
| 既定のもの(空行あり)と、その後ろに名指しのグループ    | 11-20 21:28頃 | 8.5時間後に止まる  |

止まる、
戻る、
止まるの3回が揃いました。

ここから言えることは以下の通りです。

- 名指しのグループがあれば止まり、無ければ読みに来る
- 空行の有無はどちらの向きにも関係ない
- 名指しのグループは`User-agent: *`のグループの後ろに置いても効く
- `/*/*/src/`のようなパスのワイルドカードは名指しのグループの中では効いているので、解釈はできている

パーサが壊れていてワイルドカードが読めないわけではなく、
`User-agent: *`のグループだけを相手にしていないように見えます。

名指しのグループを`*`のグループより前に置いた場合と、
名指しのグループだけにした場合は試していません。

## 反映されるのは朝6時頃

適用から切り替わりまでの時間は14.5時間、
5.5時間、
8.5時間とばらばらですが、
切り替わった時刻は3回ともJSTの朝6時前後でした。

ここだけはMetaの側の時計で考えたほうが良さそうです。
JSTの06:00はUTCの21:00で、
Metaの本社があるカリフォルニアの太平洋標準時だと13:00です。
Metaのクローラのリクエストは全てアメリカから来ていました。

UTCで見ても太平洋標準時で見ても、
日付が変わる時刻のような切りの良い時刻ではありません。
しかし平日の13時というのは、
トラブルがあった時に対応できる人員が一番居そうな時間です。
クローラの設定を反映する時刻として合理的だとは思います。
Metaがそういう理由でこの時刻にしているのかは分かりませんが。

そして`facebookexternalhit`が毎日05時台から06時台に`/robots.txt`をまとめて取得していて、
3回の切り替わりは全て、
変更の後の最初のその取得と同じ時間に起きています。
何も変えていない日にも同じ時間帯に取得しているので、
変更に反応して取りに来ているわけではなく毎日の決まった取得のようです。

`meta-externalagent`自身は`robots.txt`を取得していないので、
`facebookexternalhit`が取得した`robots.txt`をMetaの他のクローラが共有して使っているように見えます。
ただし、
1日に1回この時刻に切り替わる仕組みがあって、
`facebookexternalhit`の取得はそれとは別に同じ時間帯に動いているだけ、
という見方でも同じ観察を説明できます。
どちらなのかは外からは分かりません。

どちらにせよ`robots.txt`を変えてもすぐには反映されず、
公式ドキュメントの言う通り最大24時間待つ必要があります。
同じことを試す人は気をつけてください。

## 規格との関係

RFC 9309の[2.2.1. The User-Agent Line](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.2.1)にはこう書いてあります。

> If no matching group exists, crawlers MUST obey the group with a user-agent line with the "\*" value, if present.

名指しのグループが無い時は`*`のグループに従わなければなりません。
MUSTです。
Metaのクローラの振る舞いはこれに反しています。

名指しのグループがある時にそちらだけに従って`*`のグループを適用しないのは規格通りです。
Googleも
[How Google interprets the robots.txt specification](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt)
で"Only one group is valid for a particular crawler."と書いています。
なので名指しのグループには`*`のグループと同じ規則をもう一度全部書く必要があります。

## 前例

`*`を無視して名指しにだけ従う設計には前例があります。
Googleの広告用のクローラです。

[List of Google's special-case crawlers](https://developers.google.com/search/docs/crawling-indexing/google-special-case-crawlers)
の[AdsBot](https://developers.google.com/search/docs/crawling-indexing/google-special-case-crawlers#adsbot)などの項目には"The global user agent (`*`) is ignored."と明記されています。

ただしこれは広告を出す人が自分のサイトを見に来させているクローラなので、
事情が違います。
サイトの運営者が検索エンジン避けに書いた`User-agent: *`の`Disallow: /`で、
自分が頼んだ広告の審査まで止まってしまうと困るからです。

探せた範囲では、
AIの学習用のクローラで`*`を無視すると公式に明記している例は見つかりませんでした。

Metaがわざとそうしているのかバグなのかは、
外からは分かりません。
わざとなのではないかと推測する理由は以下の通りです。

- 公式ドキュメントが名指ししか案内していない
- 名指しのグループの中のパスのワイルドカードは効いているので、パーサが壊れているようには見えない
- AdsBotという前例がある

推測です。

# 対策

今は、
Forgejoの既定の`robots.txt`の後ろに名指しのグループを足したものを配信しています。

```text
# The default Forgejo robots.txt
# For more information: https://forgejo.org/docs/latest/admin/search-engines-indexation/

User-agent: *
Disallow: /api/
(既定のものをそのまま)
Disallow: /*repo-search-archived=*

User-agent: meta-externalagent
User-agent: meta-webindexer
Disallow: /api/
(既定のものと同じ56個のDisallow)
Disallow: /*repo-search-archived=*
```

NixOSの設定では以下のように、
`Disallow`のリストから両方のグループを生成しています。
全体は[forgejo-robots-txt.nix](https://github.com/ncaq/dotfiles/blob/master/nixos/host/seminar/forgejo-robots-txt.nix)にあります。

```nix
{
  config,
  lib,
  pkgs,
  ...
}:
let
  inherit (config.containers.forgejo.config.services) forgejo;
  # Forgejo 15の既定のrobots.txtが`User-agent: *`に断っているパス。
  # 既定のものが空行で区切っているまとまりごとに分けています。
  disallowBlocks = [
    [
      "/api/"
      "/avatars/"
      "/user/"
      "/swagger.*.json"
      "/explore/*?*"
    ]
    # 中略
    [
      "/*/*/src/"
      "/*/*/blame/"
      "/*/*/commit/"
      "/*/*/commits/"
      "/*/*/raw/"
      # 中略
    ]
    # 中略
  ];
  disallowLines = map (path: "Disallow: ${path}");
  # Forgejo 15の既定のrobots.txtと1バイトも違わない内容。
  defaultLines = [
    "# The default Forgejo robots.txt"
    "# For more information: https://forgejo.org/docs/latest/admin/search-engines-indexation/"
    ""
    "User-agent: *"
  ]
  ++ lib.concatLists (lib.intersperse [ "" ] (map disallowLines disallowBlocks));
  metaLines = [
    "User-agent: meta-externalagent"
    "User-agent: meta-webindexer"
  ]
  ++ disallowLines (lib.concatLists disallowBlocks);
  robotsTxt = pkgs.writeText "robots.txt" (lib.concatLines (defaultLines ++ [ "" ] ++ metaLines));
in
{
  # Forgejoは`custom/public/robots.txt`があると既定のrobots.txtの代わりに返します。
  containers.forgejo.config.systemd.tmpfiles.rules = [
    "d ${forgejo.customDir}/public 0750 ${forgejo.user} ${forgejo.group} - -"
    "L+ ${forgejo.customDir}/public/robots.txt - - - - ${robotsTxt}"
  ];
}
```

## ポイント

- `User-agent`の行を2つ続けて書くと、1つのグループを複数のクローラに宛てられる
- 名指しのグループには`*`のグループと同じ`Disallow`を全部書く。名指しのグループがあるクローラには`*`のグループは適用されないため
- ファイルは[`pkgs.writeText`](https://nixos.org/manual/nixpkgs/stable/#trivial-builder-writeText)でNixストアに作って、[systemd-tmpfiles](https://www.freedesktop.org/software/systemd/man/latest/tmpfiles.d.html)の`L+`でシンボリックリンクを張る
- `Disallow`のリストは既定のものを手で写したものなので、Forgejoの更新で既定のものが変わっても追従しない

追従しないのは欠点ですが、
クロールを断っているのはセキュリティのためではありません。
漏れても無駄なページを読まれるだけで大した問題にならないので、
追従する仕組みは考えていません。

## 採らなかった対策

### CloudflareやリバースプロキシでMetaを拒否する

一番簡単で確実な方法です。
他の人の報告でもnginxで403を返したりしています。

しかし門を閉めることになるので採りませんでした。
前提に書いたように、
リポジトリの最新の中身やissueを読んでもらうこと自体は歓迎しているからです。

### コミット固定のURLを最新版へリダイレクトする

`src/commit/{hash}/...`を`src/branch/master/...`へリダイレクトすれば、
総当たりは空回りします。

しかし古い版を訊かれて最新版を返すのはすり替えです。
人間が古いコミットを見たい時にも困るので採りませんでした。

### 名指しで全てを断る

名指しのグループを書くなら`Disallow: /`と書くこともできますが、
これも門を閉めることになります。

特定の相手を名指しで悪と裁くことは自分ではあまりしたくありません。
私も誰かから見れば悪かもしれませんが、
だからといって自由ソフトウェアを使うことを拒まれたくはないからです。

今回の名指しのグループは、
既定で全員に頼んでいることを、
通じる書き方でもう一度言っているだけなので許容しました。

## 誤算

一つ誤算がありました。

私としては、
トップページやリポジトリの最新の中身やissueは読んでもらって構わなかったのですが、
Forgejoの既定の`robots.txt`は`/*/*/src/`を丸ごと断っているので、
最新のブランチのファイルの表示も断っていることになります。
名指しのグループに従ったMetaのクローラは、
結果としてほとんど何も読まなくなりました。

これはForgejoの既定の判断がそうなっているという話で、
他のクローラも同じ条件です。

GitHubのミラーについては、
中身はGitHubにもあるのでそちらから読んでもらえば良いです。
しかしミラーではないリポジトリまで読まれなくなるのは少し困っています。
そちらはForgejoにしか無いからです。

# 報告

Forgejoに報告しました。

[problem: Meta's crawlers ignore the default robots.txt, but obey it once it is restated without blank lines and with a named group · Issue #15333 · forgejo/forgejo](https://codeberg.org/forgejo/forgejo/issues/15333)

タイトルは最初に報告した時のままなので空行のことが入っていますが、
その後の切り分けの結果もコメントで報告しています。

- [名指しを戻したらまた止まったという報告](https://codeberg.org/forgejo/forgejo/issues/15333#issuecomment-28377182)

Forgejoにとっての含みは以下の通りです。

- 既定の`robots.txt`から空行を除いても、Metaのクローラには効かない
- 既定の`robots.txt`をいくら整えても、`*`宛てである限りMetaのクローラには届かない
- 効かせるには、既定の`robots.txt`の後ろに名指しのグループを足すことになる
- 自分で`custom/public/robots.txt`を置く方法は、既定のものの変更に追従しなくなる

Forgejoでは既定の`robots.txt`で断るパスを増やす

このままだとMetaのクローラには届きません。

既定の`robots.txt`に特定の会社のクローラの名前を入れるかどうかは、
上流が決めることです。
必要であれば名指しのグループを足すPRを出すと伝えてあります。

issueでは、
[Metaは善意につけ込んでいるのだからブロックして当然だ](https://codeberg.org/forgejo/forgejo/issues/15333#issuecomment-28117416)、
という意見も貰いました。
インフラの管理者がブロックするのは当然の権利だと思います。
私がそうしないのは単に私の立場の問題です。

Metaには報告していません。
公式ドキュメントの末尾の[Contact us](https://developers.facebook.com/docs/sharing/webmasters/web-crawlers#contact-us)にwebmaster向けのメールアドレスが載ってはいるのですが、
メールを送っても反応があるとは思えません。
公式ドキュメントが名指しを案内している以上は、
仕様だと言われて終わりそうでもあります。

# 感想

Googleの広告Botは契約者に対して動くだけなので良いとは思うんですが、
Metaのクローラは一般的なwebクローラなので、
OpenAIやAnthropicやGoogleのクローラと同じように、
`robots.txt`の`User-agent: *`に従うべきだと思います。

私はForgejoをCloudflare Tunnelで繋いでいたことと、
10Gbps契約のネットワーク回線に余裕がありすぎたことで、
そもそも異常なクローリングをされていることに、
Cloudflareのダッシュボードを見るまで気が付かなかったぐらい、
影響がありませんでしたが、
困る人もいると思います。

このようなクロールをしていたら単純にMetaのクローラをブロックする人も多いと思います。
Forgejoの関係者のように。

私はAIクローリングをなるべく禁止したくはないので、
[RFC 9309: Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html)に従って、
普通のクローラと同じように振る舞うべきだと思います。

まあ私もクローリングを禁止されたら大人しくそれに従うべきなのか、
